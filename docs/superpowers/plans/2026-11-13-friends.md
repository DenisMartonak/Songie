# Friends (SON-34) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mutual friends:
- find Songies users in a search tab;
- send, accept, decline and cancel requests;
- a Friends page and a friend's page;
- a dot for waiting requests.

**Architecture:**
- **Server.** A `friendships` table that clients may only read their own
  rows of. All changes go through three security-definer functions.
- **App.** A `FriendsBackend` (Supabase, faked in tests) under a
  `FriendsService` that holds friends, incoming and outgoing requests. It
  refreshes on sign-in, every 5 minutes and on demand.
- **UI.** It reads the service through Riverpod providers.

**Tech Stack:** Supabase (Postgres, PostgREST, RPC), Flutter, Riverpod,
go_router, fake_async.

**Spec:** `docs/superpowers/specs/2026-11-13-friends-design.md`

## Global Constraints

- **Migration file:** `supabase/migrations/20261114120000_friends.sql`.
  - Applied by the user once, after the saved-artists migration.
  - Documented in `docs/supabase.md` as section "Friends
    (`20261114120000_friends.sql`)", with manual checks, in the style of
    the Listen together section.
- **RPC names and parameters:** `send_friend_request(p_other uuid) returns
  text`, `accept_friend_request(p_other uuid)` and `remove_friend(p_other
  uuid)`.
- **Error strings raised by the server:** `self_request`, `unknown_user`,
  `not_requested`.
- **Copy:**
  - Tab "Songies Users".
  - Buttons "Add friend", "Requested", "Accept", "Friends", "Decline",
    "Cancel", "Remove friend".
  - Empty states "Type at least 2 letters", "No Songies users found",
    "Log in to find friends".
  - The Friends page empty state: "No friends yet. Find people in Search
    under Songies Users."
- **Limits:** search starts at 2 letters, shows at most 20 people, matches
  case-insensitively by username prefix and excludes yourself. Requests
  refresh every 5 minutes while signed in.
- Run Flutter as `export PATH=$HOME/development/flutter/bin:$PATH`. Never
  boot the Android emulator.

## Review Focus

1. **Both people send a request at once.** The second
   `send_friend_request` finds the reverse pending row and accepts it,
   giving exactly one row in the end. Covered by the SQL manual check 3 in
   Task 1 and the service test in Task 3.
2. **Signing out or switching accounts** clears all friend state at once,
   so the dot doesn't carry over to the next account, and the timer stops.
   Covered in Task 3.
3. **A request action fails offline.** The UI shows a message on an
   island, the state is unchanged, and the button works again. Covered in
   Task 4.
4. **A search with `%` or `_`** matches them literally, not as wildcards.
   Covered in Task 2.
5. **Someone deletes their account.** Their rows go (cascade), and the
   next refresh drops them from your lists. Covered by SQL manual check 6
   in Task 1 and the service refresh test in Task 3.

### Task 1: Migration and its docs

**Files:**
- Create: `supabase/migrations/20261114120000_friends.sql`
- Modify: `docs/supabase.md`: a new section after "Saved artists".

**Interfaces:**
- Produces:
  - **Table** `public.friendships(requester uuid not null references
    auth.users on delete cascade, addressee uuid not null references
    auth.users on delete cascade, status text not null check (status in
    ('pending','accepted')), created_at timestamptz not null default now(),
    accepted_at timestamptz)`.
    - Primary key `(requester, addressee)`.
    - Check `requester <> addressee`.
    - A unique index on `(least(requester, addressee),
      greatest(requester, addressee))`.
  - **Access.** RLS is on. A select policy for `authenticated` allows
    `requester = auth.uid() or addressee = auth.uid()`. There is
    `grant select` only.
  - **Functions:**
    - `send_friend_request(p_other)`:
      - Raises `self_request` when `p_other = auth.uid()`.
      - Raises `unknown_user` when there is no `profiles` row.
      - If a row exists with you as addressee and it is pending, it sets it
        to accepted and returns `'accepted'`.
      - If any other row exists, it returns its status unchanged.
      - Otherwise it inserts a pending row and returns `'pending'`.
    - `accept_friend_request(p_other)`: updates the pending row
      `(requester = p_other, addressee = auth.uid())` to accepted. If there
      is none, it raises `not_requested`.
    - `remove_friend(p_other)`: deletes the pair's row in either
      direction, and does nothing if there is none.
    - All are `security definer set search_path = ''`, with
      `grant execute … to authenticated`.

- [ ] **Step 1: Write the SQL**, following the comment style of
  `20261109120000_listen_together.sql`.
- [ ] **Step 2: Write the docs section.**
  - What the migration adds, in a few bullets.
  - Manual checks, run as accounts A, B and C with the
    `set_config('request.jwt.claim.sub', …)` recipe:
    1. A requests B and gets `pending`. B selects and sees the row; C sees
       nothing.
    2. B runs `accept_friend_request(A)`, and the row is `accepted`.
       A running `accept_friend_request(B)` raises `not_requested`.
    3. Crossed requests: C requests A, then A requests C. The result is
       `accepted`, and there is one row.
    4. A requests A and gets `self_request`. A requests a random uuid and
       gets `unknown_user`.
    5. Insert, update and delete straight on `friendships` as A fail
       (permission denied).
    6. Deleting account C (from the dashboard) removes its rows.

### Task 2: FriendsBackend

**Files:**
- Create: `lib/friends/friends_backend.dart`
- Create: `test/helpers/fake_friends_backend.dart`
- Modify: `lib/providers.dart`: `friendsBackendProvider`, lazy like
  `roomBackendProvider`.
- Test: `test/friends/friends_backend_test.dart`

**Interfaces:**
- Produces:
  - `class FriendUser { final String id; final String username; final
    String? avatarUrl; }` with value `==`.
  - `enum FriendLink { friend, incoming, outgoing }` and `class FriendRow {
    final FriendUser user; final FriendLink link; }`.
  - `class FriendsException implements Exception { final FriendsError
    error; }`, where `enum FriendsError { offline, selfRequest,
    unknownUser, notRequested, other }`.
  - The interface:

    ```dart
    abstract class FriendsBackend {
      Future<List<FriendRow>> load(String me);
      Future<List<FriendUser>> search(String me, String query);
      Future<FriendLink?> send(String other);
      Future<void> accept(String other);
      Future<void> remove(String other);
    }
    ```

    `send` returns `FriendLink.outgoing` for `'pending'` and
    `FriendLink.friend` for `'accepted'`.
  - `SupabaseFriendsBackend(SupabaseClient Function() client)`, plus a
    `@visibleForTesting
    SupabaseFriendsBackend.withCalls({required rpc, required escape})`.
    - Only the RPC mapping and `escapeLike` are unit-tested.
    - `load` selects `friendships`, then `profiles` `in` the other ids,
      and builds `avatarUrl` the same way `SupabaseAccountBackend` does.
    - `search` uses `ilike('username', '${escapeLike(q)}%')`,
      `.neq('id', me)`, `.order('username')`, `.limit(20)`.
  - `String escapeLike(String q)` escapes `\`, `%` and `_` with a
    backslash.
  - `FakeFriendsBackend` (test helper):
    - an in-memory pair map and profiles;
    - an `error` to throw;
    - `calls`;
    - the same rules as the SQL: crossed requests accept, self raises.

- [ ] **Step 1: Write the failing tests**
  - `'escapeLike escapes wildcards'`: `escapeLike('a_b%c\\') ==
    'a\\_b\\%c\\\\'`.
  - `'send maps pending and accepted; server errors map'`: `withCalls`
    whose rpc returns `'pending'`, then `'accepted'`, then throws
    `PostgrestException(message: 'self_request')`. Expect `outgoing`,
    then `friend`, then `FriendsException(selfRequest)`. A
    `SocketException` maps to `offline`.
  - `'the fake follows the server rules'`:
    - A sends to B and gets outgoing. B's `load` shows A as incoming.
    - B sends to A and gets friend. Both loads show friend.
    - A sends to A and gets `selfRequest`.

**Interfaces:**
- Produces:
  - `class FriendsState { final List<FriendUser> friends, incoming,
    outgoing; final bool loaded; FriendLink? linkOf(String userId); }`.
    `FriendsState.empty` is `loaded: false`.
  - `class FriendsService`, built as
    `FriendsService(FriendsBackend backend, {Duration every = const
    Duration(minutes: 5)})`.
    - Members: `state`, `states`, `Future<void> signedIn(String me)`,
      `void signedOut()`, `Future<void> refresh()`,
      `Future<List<FriendUser>> search(String q)`,
      `Future<void> send(String id)`, `accept(String id)`,
      `remove(String id)`, `dispose()`.
    - **Actions:** they call the backend, then `refresh()`. They rethrow
      `FriendsException`.
    - **`search`:** with fewer than 2 characters after trim it returns
      `[]` without calling the backend.
    - **`signedOut`:** emits `FriendsState.empty` and cancels the timer.
    - **Providers:** `friendsServiceProvider` calls `signedIn` and
      `signedOut` from the account state (user id changes), like
      `_remoteUserIdProvider`.
